# 首次使用：从配置到一个小任务

[English](quickstart.en.md) | [返回首页](../README.md)

先准备两份文件，与总控确认分工，再试一个小任务。你不需要先研究调度脚本，也不需要把所有模型和 MCP 一次装齐。

**当前版本需要手动交接任务和记录结果。** 本仓库不会启动其他 AI、自动选模型或自动更新看板。下文的提示词用于指导已有的 AI 工具，不是启动程序。

想让 AI 帮你收集需求、填写配置？先看 [Skill 安装与测试](skill.md)。以下保留不安装 Skill 的手动方式。

## 1. 准备一个本地工作副本

需要 Git，以及你有权使用的 AI 编程工具。先确认总控、执行者和审查者能访问目标项目及任务文件；本框架不会替你登录或开通模型。

在终端执行以下命令；已有本仓库副本时，进入它并从 `mkdir` 开始：

```sh
git clone https://github.com/jake2ace/multi-model-dev-framework.git
cd multi-model-dev-framework
mkdir -p projects/my-project
cp templates/PROJECT_CONTEXT.md projects/my-project/PROJECT_CONTEXT.md
cp templates/WORKFLOW_PROFILE.md projects/my-project/WORKFLOW_PROFILE.md
```

`my-project` 可换成你的项目代号。这是协作资料目录；真正要开发的代码可以在另一个本地 Git 仓库中，把它的路径写入项目背景即可。不要把本框架的 `AGENTS.md` 或 `CLAUDE.md` 直接覆盖到已有项目。

中文用户使用上述模板；英文用户使用[英文指南](quickstart.en.md)。无需同时复制或加载两个语言版本。

## 2. 填你知道的内容，其余交给总控协助确认

| 文件 | 先准备这些信息 |
| --- | --- |
| `PROJECT_CONTEXT.md` | 要做什么、代码在哪里、允许改哪里、怎样验收、哪些限制必须遵守 |
| `WORKFLOW_PROFILE.md` | 可用模型、谁总控/执行/审查、effort、预算、失败后怎么办 |

不清楚的项保留“待确认”，不适用的项写“无”。复杂任务暂不试用时可明确写“本轮只做低等级任务，其他任务暂停”；没有接管模型时可选“修改耗尽后暂停给开发者”。不用为了填满表格启用更多模型。

在你选定的总控会话里粘贴下面的文字，替换尖括号中的内容：

```text
我想用 multi-model-dev-framework 协作完成一个小任务。
框架本地路径：<路径>
目标项目本地路径：<路径>
项目背景：<框架路径>/projects/my-project/PROJECT_CONTEXT.md
协作配置：<框架路径>/projects/my-project/WORKFLOW_PROFILE.md

本次目标：<一句话目标>
我能使用的模型：<实际可用的模型>
本轮预算：<时间、调用次数或消耗限制；不确定就请先估算>

请只读取中文版本的 README、AGENTS.md、docs/workflow.md 及上述两份输入。
如果使用 Claude，也读取 CLAUDE.md。
先检查缺项、模型可用性和目标项目已有规则，帮我补齐输入。
给我简短的启动方案：目标与验收、角色与 effort、预估调用、停止条件。
尚未核验的内容保持待确认，不要编造模型 ID 或权限。
等我确认配置再开始执行；不要自行部署、发布或合并代码。
```

**这一步的完成标志：** 两份输入已补齐本轮需要的信息，你实际确认了配置；没有影响本轮执行的阻塞项。只填文件不会自动开始任务，也不会赋予 AI 账户权限。

## 3. 手动试跑一个小任务

示例：**为一个已有命令行工具补齐 README 的安装与运行说明。** 限制为只修改该项目的 README；验收是文档与实际入口一致、没有虚构参数、示例命令得到验证或明确说明未验证。

这个例子可换成你自己范围小、结果容易检查的任务。先测小任务，更容易看清审查和交接有没有增加过多成本。

1. **总控写任务说明。** 明确修改范围、验收、执行与审查角色、effort、预计调用和暂停条件。示例文件：`tasks/T001.md`。
2. **安排执行会话。** 当前需要你在已有工具中打开已确认的执行模型会话，传入任务文件及相关项目约束。执行者完成工作，保存完整结果或代码差异位置、验证证据及摘要。
3. **安排独立审查会话。** 将原始任务、实际产出和验证证据交给已确认的审查模型。审查者记录通过/需修改、具体问题及证据；不能只看执行者摘要。
4. **把结果交回总控。** 日常决策仍只与总控讨论。总控读执行摘要与审查结论，安排修改或最终审核；你只需手动传递文件路径，无需在每个会话重讲全部背景。
5. **通过后记录结论。** 首次提交后最多修改 3 次，次数手动记录且跨会话不重置。耗尽后按配置接管或暂停；接管后仍须独立审查和最终审核，仍失败交给你决定。

可以用下面的路径区分记录；**这些只是文件命名示例，没有自动读取协议**：

```text
tasks/T001.md             目标、约束、验收、分工
outputs/T001.md           完整结果与验证证据位置
reviews/T001.md           审查意见与修改次数
summaries/T001.md         给总控看的简短进展
```

代码修改保存在目标项目的工作分支中；记录文件引用对应文件/提交位置。不要让两个执行会话同时修改同一文件。单次 Codex 运行不得超过 25 分钟，当前需要手动计时、提前切块并保存续接摘要。

**一次试跑的完成标志：** 产物存在、验收证据可检查、独立审查和最终审核都有结论。PR 或检查通过都不等于已授权合并；本框架仓库的 `main` 仍由仓库所有者决定合并。

## 4. 让总控每次只报告你最关心的内容

下面是可以要求总控使用的简短摘要样式，不代表已经运行的看板功能：

```text
任务：<ID 与目标>
进度：<已完成什么 / 当前步骤>
质量：<检查结果、证据位置、未验证项>
消耗：<已知调用次数、用时；其他指标写来源与单位>
返工：<初次提交 / 第几次修改，最多 3 次>
下一步：<继续执行 / 需要我决定的问题及原因>
```

`board.md` 目前为空。首次试用直接看摘要和审查记录即可；自动看板、计数和恢复属于后续功能。

## 怎样判断是否更省、更快

维护者将通过实际试用调整模型分工和 effort。你也可以先用同一验收标准比较“单模型完成”与“多模型分工”，而不是一开始追求最复杂的组合。

| 记录项 | 为什么要看 |
| --- | --- |
| 任务与起始版本、验收标准 | 确保比较的是同一难度和质量要求 |
| 模型、effort、是否使用 context-mode | 明确这次改了哪个条件 |
| 总用时与人工交接时间 | 把协调、审查成本也算进去 |
| 各角色调用次数、修改次数 | 判断是否因反复审查而增加消耗 |
| 可取得的用量及其来源、单位 | 分开记录 token、费用、套餐额度；未知就写未知 |
| 验收结果、遗漏和需要人工修复的问题 | 防止用降低质量换取表面节省 |

从相同起始版本分别试跑，避免后一组直接复用前一组的成果；记录缓存、后台其他任务等干扰。一次试验只能说明这一次，积累几个有代表性的任务后再形成建议。没有账单归因时，不把账户额度变化或 token 差异直接换算成精确节省比例。

context-mode 是可选项：先完成一次基础流程，再按[使用说明](context-mode.md)验证工具和统计，比较是否值得引入。查看[上游最新功能](https://github.com/mksglu/context-mode/releases/latest)不代表本机已安装或启用。

## 遇到这些情况怎么办

| 情况 | 下一步 |
| --- | --- |
| 想找启动按钮或运行命令 | 当前没有调度器，按本页手动试用；自动化需等待后续实现 |
| 不知道选什么模型或 effort | 提供实际可用模型和预算，请总控给建议，再由你确认 |
| 只有一个模型 | 可分会话试流程，但需确认审查独立性的局限；不要称为跨模型审查 |
| 模型无法访问目标仓库或任务文件 | 先解决路径和访问问题，不要让它凭摘要猜实现 |
| context-mode 不可用 | 可选时按已确认回退规则继续；必需时暂停相关任务 |
| 任务超预算或反复失败 | 按停止条件暂停，让总控说明原因和选择，不自动加预算或无限重试 |

真实项目输入、运行记录和凭据不要上传到公开仓库。欢迎在 [Issues](https://github.com/jake2ace/multi-model-dev-framework/issues) 提交脱敏后的问题或实测经验。
