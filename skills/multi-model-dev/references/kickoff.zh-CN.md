# 中文项目启动流程

## 从一个简短对话开始

先用一句话说明你会协助确定项目目标、模型分工和预算。沿用用户已给的信息，不要求重新填写长表。

首次信息不足时，优先问：要做什么和第一版功能、目标用户、已有或新建项目的位置、能使用哪些模型与预算。把最影响本轮的缺项合成一小组问题；通常每轮 1～3 个，剩余信息随方案补齐。
技术栈、effort 和预算未知时给出有理由的建议，并标记为待确认。不要把一份完整模板的每个字段都变成必须立刻回答的问题。

用户仅想讨论时停留在对话中。请求启动配置时可准备本地草案；位置没有确定时，先完成不依赖路径的方案，写入前问清目标目录。

## 提出一份能确认的方案

先检查所选项目的现有规则和文件状态。新项目不自动继承当前聊天所在目录的工程背景，也不在未指定的目录创建应用。

向用户展示简短方案：

1. 本轮目标、包含/不包含范围、可验证的验收标准。
2. 总控、执行、独立审查与最终审核的模型和 effort。明确哪些只是建议、哪些已核验；不声称当前会话已切换模型。
3. 首个任务、复杂任务的处理方式、失败接管和停止条件。
4. 调用预估与假设、时间或用户提出的预算、context-mode 是否需要。

可用的最小试用配置是一个总控、一个执行角色和一个独立审查角色；最终审核可由总控承担。这是待确认的建议，不固定要求三种模型或特定提供方。
只使用一种模型时可用独立会话试流程，说明局限，不声称跨模型审查。只有 Codex 时不要求 Claude；未配置复杂任务可以暂停该类任务，不必为了表格齐全启用新模型。

调用预估可按“执行 1 次 + 独立审查 1 次；每次修改再增加执行 1 次和审查 1 次”说明，共最多 8 次执行/审查调用；总控沟通、最终审核、切块续接和接管另计。这只是计划单位，不是精确的产品额度计费单位。没有可靠数据时不填周额度百分比。

首次提交之后最多修改 3 次；耗尽后按配置讨论并接管，无可用接管者时暂停给用户。接管成果继续独立审查和最终审核，仍失败由用户决定。预算先耗尽则先暂停。
单次 Codex 运行上限 25 分钟，提前切块并保存摘要；告知用户当前需要手动计时。特殊能力由项目单独指定，名称不代表已启用。

## 让用户选择 context-mode

启动时简短说明：大日志和大文件可能减少进入上下文的文本；代价是运行依赖、配置维护、可能的额外延迟与本地索引存储，小任务未必获益，也不保证套餐额度节省。
明确让用户选“安装并验证 / 暂不安装 / 已安装只检查”，并记录客户端和本地/全局范围。已有选择就沿用；未回答保持待选择。
选择安装或检查后，按需读取[安装与验证流程](context-mode.zh-CN.md)，实际使用工具完成已授权步骤，不只给命令让用户自己做。遇到需要重启或信任确认的步骤，记录等待状态并续接。

## 生成本地输入

选用 [项目模板](../assets/PROJECT_CONTEXT.md) 和 [协作配置模板](../assets/WORKFLOW_PROFILE.md)。由你根据对话填写，用户只确认关键决策。复制后的文件无需模板语言切换链接，移除失效的模板导航。

有用户指定的记录目录时使用它。否则，在目标项目路径明确后，建议以 `<目标项目>/.multi-model-dev/<project-id>/` 保存本地配置；这是输入文件目录，不是要提交的应用源码，也不是框架安装目录。

- 写入前查看已有文件；更新已有输入时保留用户内容、版本与有效确认，不覆盖已有的 AGENTS.md / CLAUDE.md。
- 缺少 Git 忽略保护时，可在新建 `.multi-model-dev/` 中添加内容为 `*` 的 `.gitignore` 作为本地记录保护；已有文件先读再保留式修改。在 Git 项目中用 `git check-ignore` 检查实际输入文件。强制添加仍可绕过忽略，不能宣称永远不会上传。
- 输出文件名固定为 `PROJECT_CONTEXT.md`、`WORKFLOW_PROFILE.md`，用相对路径互相引用，同时明确目标源码目录。
- 未知项写“待确认”，不适用写“无”。限定本轮任务范围，区分本轮阻塞和未来可后补字段。
- 只在用户实际认可所展示配置后写“已确认”，记录确认时间与一句简短来源；不保存完整聊天或私人账户信息。
- 已确认配置中不重复请求相同批准。角色、预算或范围实质变化时，仅重新确认变化部分。

用户要求继续试任务且配置可执行时，在记录目录内准备 `tasks/T001.md`：目标、允许修改的文件、依赖、原始验收与约束、输入文件版本、各角色与 effort、预算、停止条件、状态。已有任务时延续编号，不覆盖或重置。
相关目录按需创建，不制造空日志和假结果。不要为启动测试去调用模型账户或修改权限；context-mode 安装仅在用户已选择后按专用流程执行。

## 交接第一个任务

提供执行者和审查者可以直接使用的短提示词，引用任务文件和目标项目路径；执行者交付实际成果及验证证据，审查者读取原任务、实际差异和证据。
记录位于本轮的 `outputs/`、`reviews/`、`summaries/`，其中摘要包含结论、路径、验证、未解决问题和下一步。执行提示词要求遵守范围；审查提示词要求指出问题并给出通过/需修改结论。

第一版由用户在已有 AI 工具中手动开对应会话并传递路径；决策与问题仍回到总控。不要执行生成的提示词来假装已经启动第二个模型。
若用户另行要求自动执行，说明本包没有调度器，并先确认实际可用的执行方式与权限；不能悄悄实现新的调度系统。

结束时最多突出五项：目标验收、角色分工、预算停止条件、质量/修改次数、下一步/阻塞原因。未执行就写未执行，不把“配置已确认”写成“项目已完成”。

## 可选 context-mode 与试用记录

仅在用户选择使用时发现实际可用的 MCP 工具。大输出可通过适用的 `ctx_execute` / `ctx_batch_execute` 或索引检索处理，工具与参数以宿主暴露的定义为准。可用时通过 `ctx_doctor`、`ctx_stats` 检查；统计可读不证明 hooks 生效。
必需但不可用时阻塞相关任务；可选时按已确认的回退方案继续。启动 Skill 本身不依赖 context-mode；用户选择安装后由你完成安装与验证，不默认升级或监控。
[上游说明](https://github.com/mksglu/context-mode) · [最新功能与版本](https://github.com/mksglu/context-mode/releases/latest)。

试用后记录各角色调用、总用时、人工交接时间、修改次数和验收结果。token、费用和套餐额度分别注明来源、单位，未知值保持未知。保持相同验收标准再比较配置，不宣称未经实测的节省比例。
