# context-mode：用户选择后安装与验证

## 选择要明确，说明要简短

在启动方案中主动提供选择，不把没回答当作同意。已有明确选择时沿用，不重复问。

- **好处**：大文件、长日志和批量检索可以只把相关结果送入模型上下文；在适合的任务中可能减少输入和重复读取。
- **代价**：需要运行依赖和客户端配置；工具处理可能增加延迟，小任务未必划算；索引和会话记录可能保存在本地，需要管理磁盘和私有数据；hooks 支持随客户端版本不同。
- **效果边界**：不保证节省套餐额度或提升速度，不能把上游宣传比例当成本项目的实测结果。
- **安装范围**：仅为用户选择的客户端配置本地 context-mode，可能包含 MCP 与 hooks；不等于安装所有提供方或连接可选的外部分析服务。

可用提问：“是否为这次使用的客户端安装 context-mode？可以选：安装并帮我验证 / 暂不安装 / 已安装，只检查。它适合大输出处理，但会增加依赖和维护，实际节省需要测试。”
根据任务给出推荐理由，但不默认勾选安装。用户选跳过时，记录跳过并继续普通启动流程；不要劝到用户同意为止。

## 用户选择安装后，负责做完可执行的步骤

1. **识别目标**：确认实际客户端、运行机器/容器和配置范围。检查该环境已有插件、MCP、版本与工具，避免重复安装；不要仅凭本机存在 `.claude` 或 `.codex` 目录猜目标。
2. **核验当前上游**：读取 [官方安装说明](https://github.com/mksglu/context-mode#install)、[Releases](https://github.com/mksglu/context-mode/releases/latest) 和对应客户端现有帮助。检查所选版本的依赖；main 的说明与发布包可能不同。记录实际版本/提交和来源，不固定承诺永远支持某个版本。
3. **保存可回退信息**：只备份将改动的配置，放在公开仓库之外；报告路径而非完整内容，避免泄露已有凭据。优先客户端自己的注册工具，保留其他 MCP、插件、hooks 和项目规则。健康的已有安装直接验证，不擅自升级。
4. **执行安装与注册**：使用工具实际完成受支持的安装。用户已选择安装，不再为每条普通命令重复询问。缺少运行时、需扩大安装范围、增加权限或破坏性解决冲突时，先解释具体变化并取得对应授权再执行；已经明确授权的依赖和普通安装步骤不重复询问。不绕过宿主审批。
5. **完成验证**：按下方分层检查。不能只给教程或下载链接就说完成。需要客户端重启或用户处理信任提示时保存续接说明，把状态写成“等待重启/信任确认”，新会话再继续验证。不要强制关闭用户正在工作的会话。

安装授权只涵盖说明过的本地集成。不要顺便改认证方式、弱化审批、开启外部分析上传、安装其他客户端或删除已有索引。安装失败则停在具体诊断，必要时只回退本次修改；不无限重复安装。

## 按客户端选择路径

**Codex**：先检查 `codex plugin --help`。上游目前提供插件市场路径，可由宿主安装工具或支持的 CLI 完成。支持时使用 `codex plugin marketplace add mksglu/context-mode`，然后查看该市场实际列出的插件名称，再按 `codex plugin add --help` 安装对应项；添加市场本身不等于安装插件。若只有受支持的 UI 安装入口，使用已授权的电脑操作完成，不猜未公开的 API。

按当前官方客户端能力核验 hooks 开关和信任要求。不要把 MCP 可达当作 hooks 生效。已有插件与手工 MCP 条目发生冲突时先解释，不能同时注册两份。

旧版本或无插件能力时，使用上游明确支持的手工 MCP 路径；检查当前 `codex mcp add --help` 和 `context-mode` 包入口，合并必要配置。Hooks 仅在当前客户端确实支持时配置。若只能提供 MCP 工具，明确“仅 MCP，自动路由未验证/不可用”，由用户决定是否接受限制。

**Claude Code**：先检查当前 CLI 的插件安装帮助，使用上游 `mksglu/context-mode` 市场提供的插件安装方式；若所处宿主允许操作该客户端，代用户执行并核验。无插件路径时可按上游的 MCP-only 方式注册，需明确不含 hooks/插件命令。不要为了 context-mode 安装一个用户没选择的 Claude Code 客户端。

**其他客户端**：只读取所选客户端的上游安装段落，不批量加载所有适配器。缺少可验证安装路径时报告具体不支持项，不能复制 Codex 配置当通用配置。

无论哪条路径，检查子进程实际可见的运行时和 PATH。不要照抄上游示例的 `cp ... AGENTS.md` 覆盖已有规则；需要路由说明时审阅后合并相关部分。全局配置会影响其他项目，必须在安装选择时说明范围。

## 分层验证与记录

| 层次 | 要有的证据 |
| --- | --- |
| 已安装 | 可定位的包/插件、版本或提交及满足的运行依赖 |
| 已注册 | 目标客户端列出正确条目，配置可解析，无重复注册 |
| 当前会话可用 | 宿主实际发现工具；`ctx_doctor`、`ctx_stats` 有返回或准确说明失败 |
| 路由/钩子 | 当前客户端支持、启用并信任；实际无害测试或事件证据，不能由 stats 推断 |

按宿主实际暴露的参数调用工具。可用一个不读取用户资料的合成小样本测试 `ctx_execute`，并核对输出。若要验证 hooks，使用上游定义的无害匹配场景；仅配置了 hook 文件时写“已配置，运行未验证”。
在已有记录写入授权及明确路径时，将安装方式、版本、配置范围、备份位置、工具检查结果、hooks 状态和待处理事项保存到本地协作记录。仅检查且未授权写入或位置未确定时，只在对话报告，不自动新建文件。不保存凭据或上传诊断全文。

用户选择“已安装，只检查”时先做只读检查；发现问题后解释修复动作并取得授权，不能把检查升级为重装或升级。
安装偏好与运行要求分开：必需能力不可用时暂停相关任务；可选时按已确认回退方案继续。结束报告清楚区分“安装完成”和“集成验证完成”。
